## 三、发现的问题

### 🟠 建议修改

**[建议修改] 规则 3 终态化路径绕过 `_do_linear_complete` 收尾抽象** ✅ **已修复（commit `817099e`，2026-11-08）**

📍 `controller/core.py` `_seal_watchdog_pass` 规则 3 / 规则 2 cardless 分支

watchdog 终态回收直接执行 `session.state = COMPLETED → enter_terminal() → flush.mark_completed() → _release_session_data()` 四连，且先手动置 `state` 再调 `enter_terminal()` 的顺序暗示 enter_terminal 内部有状态前置检查——这是绕过抽象直接操作私有状态的写法。规则 2 拆卡后的 `on_completed` 正常走 `_do_linear_complete`（带 footer/统计），两条终态路径的收尾步骤集不同。

影响：当前行为无 bug（测试全绿），但若 `_do_linear_complete` 收尾以后增加新步骤（如 metrics 上报、webhook），watchdog 路径不会自动同步，产生隐性状态分歧。

**修复记录**：提取共享 `_finalize_terminal(session, *, phase, reason, source, mark_flush=True)`（UnifiedControllerMixin），三处调用点收敛（watchdog×2 mark_flush=True / reentry mark_flush=False 并保留已终态分支的裸 release 以维持原无条件释放语义）。评审时"先置 state 再 enter_terminal 疑有前置检查"的推测经核实修正：`enter_terminal` 只记录 reason/source 不负责 state，二者为全仓成对惯用法。验证：py_compile + ruff 全过，全量 1150 passed，单文件 3 次 stash 对照警告逐条一致（行为等价）。

### 🟡 建议关注

**[问题] `_seal_lock.locked()` 检查的 TOCTOU 窗口**

📍 `controller/core.py` `_seal_watchdog_pass` 规则 1 / 规则 2 / 规则 3

watchdog pass 里 `not session._seal_lock.locked()` 检查与 `_dispatch_watchdog_*` 派发之间存在窗口：检查时锁空闲、派发后正常封卡协程恰好拿锁开始执行。当前有 `_seal_done` 锁内二次判重兜底，无 bug；但正确性依赖 `_seal_done` 在所有封卡路径上被正确置位。建议在 `_seal_reentry_finalize` 入口加一条 DEBUG 日志（msg + 触发来源），方便日后排查竞态时序。
